# Контекст проекта: система управления VR-шлемами Meta Quest

Отвечай на русском. Я фронтенд-разработчик (React, Next.js, TypeScript, ~3 года). Android, ADB и Kotlin для меня новые: объясняй такие вещи простыми словами, без веб-аналогий, через то, что реально происходит в системе.

Подробная документация (как всё работает, схемы, протокол): https://claude.ai/artifact/RPWd7KQq72MycnYtQAEqJn

## Что строим

Внутренний инструмент для управления нашими шлемами Meta Quest на VR-арене. Не на продажу.
Решено писать **свою реализацию**. Готовые MDM (ManageXR, ArborXR и т. п.) не используем, не предлагай их.

## Ключевые факты

- **Dev mode на шлемах включён всегда** (специфика работы команды). Можно опираться на ADB и права `shell`.
- Стать Device Owner на Quest нельзя: это доступно только партнёрам Meta (HMS). Кнопку Meta заблокировать нельзя, можно только замечать выход и возвращать игрока в игру.
- Сервер управлять шлемами по ADB **не будет**: `adb tcpip` пропадает после перезагрузки шлема, вернуть можно только кабелем (тест 31.10). ADB на сервере не используем, `@devicefarmer/adbkit` не нужен.

## Архитектура (решено 01.11)

```
Сервер ──WebSocket──► Агент на шлеме
                       ├─ B — основа MVP: обычные права приложения (выданы кабелем один раз):
                       │     онлайн, батарея, текущая игра, запуск игр, наше меню, возврат в игру,
                       │     отключение сна (prox_close из обычного приложения — проверено)
                       └─ C — дополнение: локальный ADB (агент сам входит в adbd по ключу):
                             закрыть игру (force-stop), перезагрузка
```

- **B не зависит от ключа и от C.** Если C не поднят (после включения ещё не нажали «Allow», ключ потерян), шлем на дашборде онлайн, видны батарея и игра, игры запускаются. Недоступны только сильные команды — агент отвечает `ack { ok: false, reason: "no_adb" }`.
- **Сервер не знает про ADB.** Он отправляет только смысловые команды (`launch`, `close_game`, `reboot`, `disable_sleep`). Агент сопоставляет их с **заготовленными** shell-командами. Произвольный shell с сервера выполнить нельзя. Пакет игры проверяется по `^[a-zA-Z0-9_.]+$` перед подстановкой в shell.
- **На сервере ключей нет вообще.** Копия ключа на сервере отклонена: она помогает, только если агент потерял свою копию, а шлем ключу ещё доверяет (редкий случай, зависит от нас). Если же шлем забыл ключ (31.10 так случилось), копия бесполезна. При любой потере ключа — повторная настройка кабелем.

### Что делает оператор

1. **Один раз на шлем, по кабелю** — `scripts/provision.sh`: ставит агента, выдаёт права, создаёт ключ; оператор в шлеме ставит галочку «Always allow from this computer».
2. **После каждого включения/перезагрузки шлема** — надеть шлем и нажать **«Always allow on this network»** в окне «Allow wireless debugging on this network?». Дашборд показывает у шлема `waiting_confirmation`, пока не нажато. Именно «Always allow», не «Allow»: «Allow» разрешает один раз, и после первого же обрыва Wi-Fi окно появится снова (проверено 01.11); «Always allow» действует до следующей перезагрузки.
3. **Если ключ потерян** (статус `key_rejected`) — снова `provision.sh` по кабелю.

### Как устроен C (локальный ADB)

- Зачем `adbd`: команда работает с правами того uid, который её запустил. У приложения прав мало, у пользователя `shell` (uid 2000) — много. Получить права `shell` можно только через `adbd`; своего API для этого в Android нет, поэтому в агенте — маленький ADB-клиент (как в `spike/adb-probe/.../LocalAdb.kt`).
- «Allow» в окне доступ агенту **не даёт**: оно включает службу беспроводной отладки. Кого пускать, служба решает по ключу из `/data/misc/adb/adb_keys` — туда ключ агента попадает при настройке (только с галочкой «Always allow», иначе `CERTIFICATE_VERIFY_FAILED`).
- Порядок при каждой загрузке: дождаться Wi-Fi → `adb_wifi_enabled = 1` (через `WRITE_SECURE_SETTINGS`) → ждать, пока оператор нажмёт «Allow» (статус `waiting_confirmation`, ждать без ограничения по времени) → найти порт через mDNS `_adb-tls-connect._tcp` (порт каждый раз новый; mDNS может отдавать и старую запись с мёртвым портом — перебирать все) → войти в `127.0.0.1:<port>` по TLS 1.3 с ключом агента → `adb: ready`. (`prox_close`, который слетает при загрузке, агент под защитой применяет сам обычным broadcast'ом сразу после старта — ADB для этого не нужен.)
- Почему «дождаться Wi-Fi»: `adb_wifi_enabled = 1` переживает перезагрузку, но система проверяет его через ~20 с после старта, до подключения Wi-Fi, и сбрасывает в `0` (`Not connected to any wireless network. Not enabling adbwifi`). Данные потом идут через `127.0.0.1`, но без Wi-Fi Android отладку не включает.
- Почему окно после каждого включения: Quest **не помнит** «Always allow on this network» после перезагрузки (тот же BSSID; при загрузке `AdbDebuggingManager: Ignoring tag 'null'` — похоже на ошибку Meta, прошивка от 25.09.2026 актуальная). Внутри одной загрузки помнит: повторное включение отладки и обрыв Wi-Fi окно не вызывают. Accessibility-сервис нажать окно не может — Quest не передаёт ему события этого окна (проверено 01.11). Идеи на потом: опрашивать окна по таймеру; сообщить Meta об ошибке.
- Обрыв Wi-Fi: Android выключает отладку (`Wifi disabled. Disabling adbwifi`) и сам не включает обратно — агент слушает подключение к сети (`ConnectivityManager.NetworkCallback`) и снова пишет `adb_wifi_enabled = 1` (окна нет), затем ищет новый порт.
- Окно USB-отладки с незнакомым ключом подтверждать **нельзя** (так чужой компьютер получит доступ к шлему).
- Без процесса-помощника: агент шлёт заготовки прямо в `adbd` и переподключается перед командой, если соединение пропало. Помощник в стиле Shizuku — только если обрывы станут проблемой.
- Без `shell` (только на B) не работают: перезагрузка; полноценное закрытие игры (`killBackgroundProcesses` в Android 14 закрывает только свои процессы — проверено ❌). Без C «закрыть игру» = вывести наше меню поверх игры, процесс игры остаётся в фоне.

### Таймер ключа (7 дней)

Android удаляет доверенный ключ, если им не пользовались `adb_allowed_connection_time` мс (по умолчанию 604800000 = 7 дней; в журнале `authWindow = 604800000`; на нашем шлеме настройка не задана). Отсчёт от последнего подключения.
1. `provision.sh`: `settings put global adb_allowed_connection_time 0`.
2. Агент при каждом старте: прочитать `Settings.Global`, если не `0` — записать `0` через `Settings.Global.putLong` (`WRITE_SECURE_SETTINGS`). Нет права → `adbTimeoutDisabled: false`, статус «нужна настройка кабелем».
3. Поле `adbTimeoutDisabled` в `status`; дашборд предупреждает, если `false`.

### `scripts/provision.sh` (по шагам)

`adb install -r` → `pm grant ... WRITE_SECURE_SETTINGS` и остальные права → включить Accessibility-сервис агента (`settings put secure enabled_accessibility_services ...` + `accessibility_enabled 1`) → таймер `0` → `adb keygen` во временную папку → запустить adb-сервер так, чтобы шлему предъявлялся **только** этот ключ (adb ищет ключ только в `<домашняя папка>/.android/`, `ANDROID_USER_HOME` он не читает — проверено по adb 1.0.41; на Mac папку можно подменить через `HOME`, на Windows adb берёт папку профиля у системы, и переменные не помогают. Поэтому программа Arena на время настройки откладывает ключ компьютера в `.android/arena-computer-key/`, кладёт на его место ключ шлема и потом возвращает; после сбоя возвращает при запуске) → оператор ставит галочку «Always allow from this computer» → проверить по `logcat` (`AdbDebuggingManager ... alwaysAllow = true`), иначе стоп → передать ключ и сертификат агенту broadcast'ом в receiver с `android:permission="android.permission.DUMP"` (PKCS#8 DER + X.509 DER, base64) → удалить файлы ключа с компьютера → перезагрузка, оператор нажимает «Allow», ждать `adb: ready`.

- Сертификат к ключу — самоподписанный, как у `adb`: `C=US, O=Android, CN=Adb`, `basicConstraints=critical,CA:TRUE`, `keyUsage=critical,keyCertSign,cRLSign,digitalSignature`, `subjectKeyIdentifier=hash`.
- `DUMP` — право уровня `development`, его можно выдать любому приложению через `pm grant`, так что «отправить может только `shell`» — не абсолютная гарантия.
- Идентификатор шлема для сервера — `ANDROID_ID`, который агент берёт **сам**: у приложения он свой и не совпадает с `adb shell settings get secure android_id` (проверено: `c1f36e29…` против `efbbca1c…`).

### Статусы ADB (поле `adb` в `heartbeat`)

`ready` · `no_wifi` · `waiting_confirmation` (окно «Allow wireless debugging» не подтверждено) · `connecting` · `key_missing` · `key_rejected` · `error`. Полный протокол — в разделе «Система целиком».

## Система целиком (решено 01.11)

```
                    Локальная сеть арены (интернет не нужен)
┌──────────────────────────────────────────────────────────────┐
│  Компьютер арены                                             │
│  ┌──────────────────────────┐      ┌───────────────────────┐ │
│  │ server (Python, FastAPI) │◄────►│ dashboard (React+Vite)│ │
│  │  • WS /agent  ◄──────────┼──┐   │  REST + WS /live      │ │
│  │  • REST /api, WS /live   │  │   └───────────────────────┘ │
│  │  • SQLite                │  │                             │
│  └──────────────────────────┘  │ WebSocket по Wi-Fi          │
└────────────────────────────────┼─────────────────────────────┘
                        agent (Kotlin) на каждом шлеме
```

### Идентификация шлема

- `provision.sh` читает **серийный номер** (`adb shell getprop ro.serialno`; само приложение его прочитать не может), оператор вводит **название** («Шлем 07», наклейка на корпусе). Сервер создаёт запись и выдаёт агенту `headsetId` + секретный **токен** (на сервере хранится только хеш). Агент получает их, адрес сервера и ключ ADB тем же broadcast'ом с `DUMP`.
- Агент представляется `headsetId` + токеном при каждом подключении — чужое устройство не выдаст себя за наш шлем.
- После сброса к заводским `provision.sh` находит шлем по серийному номеру и привязывает к той же записи — история и статистика сохраняются. `ANDROID_ID` агента храним как вспомогательный (меняется при сбросе к заводским).

### Сервер (`server/`): Python + FastAPI

- **FastAPI** (REST `/api`, WebSocket `/agent` для агентов и `/live` для дашборда), **uvicorn**, **Pydantic v2** — схемы сообщений (дискриминированное объединение по полю `type`).
- **SQLite** через **SQLAlchemy 2.0** (async, `aiosqlite`) + миграции **Alembic**. На PostgreSQL — позже, если понадобится.
- **uv** для зависимостей, **pytest** + `httpx` для тестов.
- Запускать **одним процессом uvicorn** (без `--workers N`): реестр онлайн-шлемов и открытые WebSocket живут в памяти процесса.
- Модули: `agents` (подключения, проверка токена, heartbeat; офлайн — нет heartbeat 15 с или соединение закрыто), `registry` (состояние шлемов в памяти + снимки в БД), `commands` (`id`, статус `sent → acked/failed/timeout`, **срок жизни ~10 с** — команда для офлайн-шлема не выполнится неожиданно позже), `events` + `stats` (журнал и сессии), `live` (рассылка изменений на дашборд).
- Типы для дашборда: REST — из OpenAPI FastAPI (`openapi-typescript`); сообщения WebSocket — из JSON Schema моделей Pydantic (`json-schema-to-typescript`). Источник истины — Pydantic-модели в `server/`. Агент повторяет тот же JSON (kotlinx.serialization).

### Статистика

Считаем по шлему и по игре: время игры, число сессий, возвраты в игру (из каких игр чаще «сбегают»), износ батареи (скорость разряда по шлему со временем), обрывы связи по шлему (проблемные зоны Wi-Fi), время от включения до `adb: ready`. **По игрокам — нет**: шлем не знает, кто его надел (позже можно привязывать сессию к брони вручную).

### Протокол агент ↔ сервер

| Сообщение | Направление | Содержимое |
|---|---|---|
| `hello` | агент → сервер | `headsetId`, `token`, `agentVersion`, `androidId` |
| `welcome` | сервер → агент | время сервера, настройки (частота heartbeat, охраняемая игра) |
| `heartbeat` | агент → сервер, раз в 5 с | `battery`, `charging`, `temp`, `currentPkg`, `adb`, `sleepDisabled`, `adbTimeoutDisabled` |
| `event` | агент → сервер | смена игры, возврат в игру, смена статуса ADB |
| `apps` | агент → сервер | установленные игры с названиями |
| `command` | сервер → агент | `id`, `cmd` (`launch`, `close_game`, `reboot`, `disable_sleep`, `show_menu`, `guard`), параметры, `ttl` |
| `ack` | агент → сервер | `id`, `ok`, `reason` (`no_adb`, `not_allowed`, `failed`, `expired`) |

### Агент (`agent/`)

Foreground-сервис со старта по `BOOT_COMPLETED`; WebSocket через OkHttp, переподключение с паузой 1 → 2 → 5 … 30 с. Сразу после старта приводит сон в соответствие с защитой (`prox_close` под защитой, иначе `automation_disable`). Текущая игра — по событиям Accessibility. C — `LocalAdb` + `MdnsFinder` из тестового приложения, статус `waiting_confirmation` до «Allow». Адрес сервера — фиксированный, задаётся при настройке.

### Дашборд (`dashboard/`)

React + Vite (решено 01.11, вместо Next.js). Список шлемов (название, онлайн, батарея, игра, статус ADB); выбор нескольких → запуск, закрытие, меню, сон, перезагрузка; страница статистики. Вход по общему паролю (см. «Вход на дашборд»), доступ только из локальной сети.

## Структура репозитория

- `server/` — Python, FastAPI, SQLite. Реестр шлемов, WebSocket для агентов и дашборда, API, статистика. Ключей ADB не хранит.
- `dashboard/` — React + Vite + TypeScript + Tailwind. Не Next.js: SSR и API routes не нужны, бэкенд целиком в FastAPI. В разработке `npm run dev` (прокси `/api`, `/live` на FastAPI в `vite.config.ts`); на арене `npm run build`, и FastAPI сам раздаёт `dashboard/dist` на «/» — один процесс, один порт, Node на арене не нужен.
- `agent/` — Android, Kotlin. Кто пишет — решаем в команде.
- `scripts/provision.sh` — разовая настройка шлема кабелем.
- `spike/adb-probe/` — тестовое приложение для проверок. Не основа агента; `LocalAdb.kt` и `MdnsFinder.kt` можно перенести в агента.

## Защита (04.11, агент 0.9.1)

Проверено на шлеме (0.9.0, эта логика не менялась): выход игрока → возврат; сервер остановлен: через 12 с защита ещё действует, через 40 с снята (кнопка `SHUT_OFF`, сон `DISABLED`, возврата в игру нет); сервер запущен → защита снова действует и возвращает игру; «Перезапустить игру» (новый pid); кнопка питания → игра запущена заново за 0,3 с (на 0.8.0).

Один переключатель «Защита» на дашборде объединяет: возврат в игру, запрет сна при снятии, блокировку долгого нажатия питания, пробуждение после короткого. Команда прежняя — `guard`; сон и кнопку агент переключает сам внутри `Guard.set`. Отдельного переключателя сна больше нет (команда `set_sleep` осталась в протоколе, дашборд её не шлёт).
- **Сон отключён только под защитой.** Без защиты снятый шлем засыпает и уходит в офлайн: запустить на нём игру с дашборда не получится, пока его не разбудят. Включение защиты заранее (агент 0.9.0) попробовали и по решению пользователя убрали.
- Защита включается, только если идёт игра. «Закрыть игру» выключает защиту, но только после успешного закрытия. Перед `force-stop` агент ставит `Guard.hold(15 с)`, чтобы защита не вернула игру.
- **Кнопка питания под защитой:** иначе игра теряет связь со своим сервером, поэтому после короткого нажатия агент будит шлем, закрывает игру и запускает заново (`input keyevent KEYCODE_WAKEUP; am force-stop …` через локальный ADB). Событие `power_restart`: на сервере старая сессия заканчивается с `power_button`, открывается новая. Нужен ADB (`ready`): без него шлем не разбудить, он останется спать. Двойное нажатие даст два перезапуска подряд.
- **Без связи с НАШИМ сервером защита не работает** (связь с сервером самой игры агент не видит): через 30 с без связи снимаются возврат в игру, блокировка кнопки, запрет сна, реакция на кнопку; настройка защиты при этом сохраняется. Связь вернулась — защита действует снова, и если игрок не в игре, игра запускается. 30 с нужны, чтобы короткий обрыв Wi-Fi не снимал защиту. После старта агента защита не действует до первого подключения к серверу.
- **Перезапустить игру** (`restart_game`, через локальный ADB): `force-stop` → проверка `pidof` → запуск заново, защита сохраняется. Цель: `pkg`, иначе текущая игра, иначе охраняемая. На сервере старая сессия заканчивается с `end_reason = restarted` и сразу открывается новая; в статистике считается как «завершил оператор».

## Питание с дашборда (04.11, агент 0.10.1)

Команды `sleep` и `power_off` через локальный ADB (`input keyevent KEYCODE_SLEEP`, `reboot -p`). `sleep` не вызывает перезапуск игры под защитой (`Guard.expectSleep`). Агент передаёт `screenOn` (`PowerManager.isInteractive`); карточка показывает «спит». «Выключить» — с подтверждением.

Пробуждение с дашборда убрано по решению пользователя: шлем на связи только ~2 мин сна (проверено 04.11: `wake` работал через ~1 мин, через 2 мин связь пропала, ping и ADB не отвечали; возможно, из-за `wifi_power_save=120`, не проверялось). Будить шлем — кнопкой или надев его.

## Обновление агента по Wi-Fi (07.11, агент 0.11.3 — проверено на шлеме 203)

Проверено: 203 обновился с 0.11.2 до 0.11.3 без кабеля за 6 с.

Обновляет сам агент, без кабеля и без доверия компьютеру: команда `update_agent` (`versionCode`, `sha256`, `path`) идёт только через `POST /api/setup/update-wifi` с компьютера-сервера, обычным `/api/commands` её отправить нельзя (403). Агент скачивает `GET /api/agent/apk`, проверяет SHA-256, копирует через локальный ADB в `/data/local/tmp`, отвечает `ack` и выполняет `pm install -r`, держа соединение с adbd открытым (таймаут чтения 3 мин). `nohup … &` не работает: команда не запускалась, adbd, судя по всему, завершал её вместе с соединением (0.11.0, журнал установки не создавался). Android сам завершает агента в конце установки, новый поднимается сам. Ошибка — событие `update_failed` с причиной. Ход: события `update_progress` (`downloading` + проценты, `installing`), сервер держит `update` в `HeadsetView` и шлёт через `/live`, в журнал не пишет; при новом `hello` поле сбрасывается.
- Нужен ADB `ready` на шлеме. Первое обновление до 0.11.2 — кабелем: старые агенты этой команды не знают (`needs_cable`).
- Android ставит только APK с той же подписью и не ниже установленной версии.
- Список на вкладке Setup берётся из реестра: версия из `hello`, статус по `fleet_status`.

## Вход на дашборд (07.11)

- Первый запуск: пароль задаётся только с компьютера-сервера. Забыли: кнопка Reset password в окне Arena, все сессии перестают действовать.

## Кнопка питания (01.11, агент 0.5.0 — проверено на шлеме)

Политика кнопки на нашем Quest (`dumpsys window policy`): короткое — `SHORT_PRESS_POWER_GO_TO_SLEEP`, долгое — `LONG_PRESS_POWER_SHUT_OFF`, очень долгое — `VERY_LONG_PRESS_POWER_OFF`.
- Долгое: пока включена охрана, агент пишет `power_button_long_press = 0` и `power_button_very_long_press = 0` в `Settings.Global` (ничего не делать); при выключении охраны — удаляет (заводское поведение). Ожидание: AOSP берёт это поведение из настроек — проверить, что Quest тоже.
- Короткое (сон) настройкой не отключается (только конфигурация прошивки, `mShortPressOnPowerBehavior=1`). Агент ловит `ACTION_SCREEN_OFF` при включённой охране и будит шлем `input keyevent KEYCODE_WAKEUP` через локальный ADB, охрана возвращает игру. Проверено: долгое нажатие больше не выключает (`LONG_PRESS_POWER_NOTHING`), удержание ведёт себя как короткое; после сна шлем просыпается через ~2,5 с (почти всё — вход в adbd), игра продолжается. Пользователя это устраивает; ускорение (wake lock с пробуждением экрана) — по желанию.
- Удержание ~10 с — аппаратное принудительное выключение, не блокируется никак.
- Дашборд: переключатель показывает вкл / выкл / частично по выбранным шлемам; защита включается на текущую игру каждого шлема (`guard {current: true}`); «Запустить» при включённой защите ставит новую игру под защиту. Кнопка «Выйти в меню» убрана (наше меню показывается после «Закрыть игру»).

## Правила работы со шлемом

- **Не делать `am force-stop com.arena.agent`.** Android при этом выключает Accessibility-сервис агента (`enabled_accessibility_services` становится пустым) и не запускает агента снова — шлем уходит в офлайн, пропадают текущая игра и охрана. Случилось 01.11, восстановлено вручную `settings put secure enabled_accessibility_services com.arena.agent/com.arena.agent.WatcherService`. Новые права (`pm grant`) применяются без перезапуска; обновление агента — `adb install -r` (агент перезапускается сам).

- **Шлем 207 (`1WMHH868671295`) не трогать:** ни команд, ни установки, ни обновления, ни проверок на нём (сказано пользователем 07.11). Проверять на 203 (`1WMHHA717K3282`).
- Читающие команды (`devices`, `getprop`, `dumpsys`, `pm list`, `settings get`) выполняй свободно.
- Перед командами, которые меняют состояние шлема (`reboot`, `force-stop`, запуск игр, `settings put`, `pm grant`, broadcast, установка пакетов, авторизация ключей), коротко скажи, что сделаешь, и дождись моего «да».
- Никогда не делай factory reset, не удаляй приложения, не нажимай/не вызывай отзыв разрешений отладки.
- Никогда не выводи в чат, логи и коммиты закрытые ключи. Файлы ключей — в `.gitignore`.
